-Runnables Primitive->Definition: They are fundamental building blocks (or composition tools) in LangChain designed to define how execution flows between runnables.
                    ->Purpose: They replace custom glue code by providing built-in operators and methods to structure workflows (e.g., sequential, parallel, conditional, etc.).
                    ->example
                      RunnableSequence()->runs steps in order(|)
                      Runnableparallel->Runs Multiple steps simultaneously
                      RunnableMap->map the smae input across multiple function
                      RunnableBranch->implemments conditional execution
                      RunnableLambda->wraps custom python functions into runnables
                      RunnablePastthrough->just forwards input as output


-Key Runnable Primitives & Their Uses
1. Runnable Sequence (| operator)
                            Purpose: Runs multiple steps sequentially, where the output of one component automatically becomes the input for the next.
                            Syntax: chain = prompt | model | parser
2. Runnable Parallel ({})
                            Purpose: Executes multiple runnables simultaneously with the exact same input, returning a dictionary of results.
                            Use Case: Generating multiple distinct outputs from a single prompt (e.g., creating a tweet and a LinkedIn post at the same time).
3. Runnable Passthrough
                            Purpose: Passes the input data through unchanged while allowing it to be routed alongside other parallel operations.
                            Use Case: Retaining original variables (like a user's initial query) so they can be combined downstream with LLM outputs.
4. Runnable Lambda
                            Purpose: Wraps custom Python functions into runnables so they can be seamlessly integrated into LangChain pipelines.
                            Use Case: Performing custom transformations, data parsing, or utility checks (like word counting) inline.
5. Runnable Branch
                              Purpose: Introduces conditional logic into workflows, routing inputs to different chains based on specific criteria or conditions.

Text SPlitting-> It is a process of breaking large chink of text like articles
                 PDFs,HTML pages or books into cmaller manageable pieces than an llm can handle effectively
                
3 key reasons why text splitting is required for LLM-based applications:

Overcoming Model Context Limits: Large language models (LLMs) have a strict maximum input size or token limit. Sending massive documents (such as books or thousands of pages) all at once exceeds this threshold, making text splitting necessary to process data successfully within model constraints.

Better Downstream Task Performance: Breaking text into smaller chunks improves the quality of critical tasks like embeddings (capturing semantic meaning more accurately), semantic search (retrieving more precise query results), and summarization (reducing hallucinations and context drift).

Optimizing Computational Resources: Working with smaller text chunks is more memory-efficient and reduces hardware or computing requirements, which also allows for better parallelization of data processing tasks.

Core Concepts: Chunk Size & Chunk Overlap
Chunk Size: The maximum number of characters (or tokens) allowed in a single chunk.

Chunk Overlap: The number of characters/tokens shared between consecutive chunks.

Purpose: Prevents abrupt context loss when sentences or paragraphs are split midway.

Best Practice: Typically set to 10% to 20% of the chunk size (e.g., if chunk size is 500, overlap can be 50–100).

Types->>

Length-Based Text Splitting
                Core Concept:
                The simplest and fastest method of splitting text where you pre-determine the fixed size of each chunk.
                You explicitly define a character size (or token count) limit.

                How->
                The algorithm traverses the text sequentially and creates a chunk as soon as the specified character/token limit is reached, then repeats the process for the remainder of the text.

                Key Limitations:
                It does not check for meaning, grammar, or linguistic structure.
                Because it strictly cuts off at a set length, it can abruptly split words, sentences, or paragraphs in the middle, which can negatively impact the quality of downstream tasks like vector embeddings.

2. Structure-Based Splitters (RecursiveCharacterTextSplitter)Overview: Most widely used industry standard.Mechanism: Recursively splits text using a hierarchy of separators (\n\n $\rightarrow$ \n $\rightarrow$   $\rightarrow$ "") until chunks fit the target size.Pros: Preserves sentence and paragraph boundaries as much as possible.Cons: Slightly more complex.

3. Document-Specific Splitters (Language-Specific)Overview: Custom splitters designed for structured files (e.g., Python/JS code, Markdown).Mechanism: Uses syntax-aware tokens like classes, functions, or markdown headers.Pros: Keeps code blocks and logical syntax intact.Cons: Limited to specific file formats

4. Semantic Splitters (SemanticChunker)Overview: Advanced splitters based on semantic meaning.Mechanism: Uses embeddings to measure cosine distance between consecutive sentences. Triggers a split if similarity drops sharply based on a threshold (such as Standard Deviation or Percentile).Pros: Groups text strictly by semantic topic shifts.Cons: Computationally expensive and currently experimental


Frequently Asked Interview Questions & Answers
Q: Which text splitter should you use by default in production?
     A: RecursiveCharacterTextSplitter. It is robust, handles hierarchy gracefully, and prevents awkward mid-sentence breaks.

Q: What happens if your chunk size is too small vs. too large?
   Too Small: Loses broader context and global meaning.
  Too Large: Dilutes semantic search precision, introduces noise, and risks exceeding token limits or causing LLM hallucination.

Q: How do you connect Document Loaders with Text Splitters?
     A: Load raw documents into Document objects (e.g., via PyPDFLoader), then pass the resulting documents into the text splitter's .split_documents() method.

Vector Stores ->
   It is a system designed to store and retrieve data represented as numerical vectors.
   
Features->
Storage-> Ensures that vectors and their associated metadata are retained. Whether in-memory (RAM) for quick lookups or on-disk (Hard disk) for durability and large-scale use.
Similarity Search->Helps retrieve the vectors most similar to a query vector.
Indexing ->Provides a data structure or method that enables fast similarity searches on high-dimensional vectors.

CRUD operations-> Manage the lifecycle of data—adding new vectors, reading them, updating existing entries, removing outdated vectors.

Use Cases

Vector Stores vs. Vector Databases
Vector Store:
A broader term/abstraction for any system or library that indexes and stores numerical vectors to perform similarity searches.
Can be purely in-memory libraries (like FAISS) that require custom handling for persistence, data updates, and metadata.

Vector Database:
A dedicated database system specifically engineered to manage vector data with full database capabilities.
Natively handles CRUD operations (Create, Read, Update, Delete), data persistence on disk, built-in metadata filtering, security, scalability, and high concurrency out of the box.

Chroma vs. FAISS: Which is Best and When to Use?
1. FAISS (Facebook AI Similarity Search)
What it is: A high-performance open-source similarity search library developed by Meta.

Key Strengths: Blazing fast search speed, excellent memory efficiency, supports millions/billions of vectors, and provides native CPU/GPU acceleration.

When to use:

Working with massive scale datasets (millions of vectors).

Raw speed, low latency, and high throughput are your top priorities.

You are building a custom search engine backend and don't mind managing persistence/metadata separately.

2. Chroma (ChromaDB)
What it is: A lightweight, developer-friendly vector database.

Key Strengths: Incredibly easy setup (pip install chromadb), built-in local persistence (saves directly to disk), and out-of-the-box native support for storing raw text, metadata, and running metadata filters.

When to use:

Rapid prototyping, local testing, and small-to-medium RAG applications.

You want an easy developer experience (DX) without dealing with complex lower-level index configurations.


Vector Stores in LangChainUnified Interface: LangChain provides a standard abstraction layer for vector stores, meaning you can swap out backends (e.g., switching from Chroma to FAISS) with minimal changes to your core application logic.Core Operations Supported:add_documents 

from_documents: Embeds text chunks and saves them into the store.similarity_search: Queries the store using an embedding model to retrieve the top-$k$ most contextually relevant documents.delete: Removes records by ID.

Common Integration Examples:
Chroma: from langchain_community.vectorstores import Chroma (Best for local persistence & metadata filtering).
FAISS: from langchain_community.vectorstores import FAISS (Best for high-speed, in-memory processing).

4)Multi-Query Retriever->
->What it is: An advanced retriever designed to handle ambiguous, vague, or broad user queries by automatically generating multiple variations of the query using an LLM.
->Core Philosophy: Solves the problem of poor retrieval results caused by a single, poorly phrased user query. It expands the search perspective to maximize document recall.
->How It Works:
		->Query Input: The user submits a query (e.g., "How can I stay healthy?").
		->LLM Query Generation: The query is sent to an LLM, which generates multiple related but distinct sub-queries (e.g., "What are the best foods to eat?", "How often should I exercise?", "How to manage stress?").Parallel Retrieval: Each generated query is sent independently to the underlying retriever (such as a vector store similarity search) to fetch matching documents.
		->Merge and Deduplicate: All retrieved document lists are merged, duplicate documents are removed, and the top unique results are returned to the user.
->When to Use-->
		->When user queries are short, broad, or ambiguous.
		->When a standard similarity search misses relevant context due to a single narrow keyword interpretation


.2. Contextual Compression Retriever
->What it is: An advanced retriever that improves retrieval quality and precision by compressing or trimming documents after they are retrieved, keeping only the specific content relevant to the user's query.
->Core Philosophy: Standard retrieval might pull up a large document because it matches the query topic, but that document could also contain plenty of irrelevant information (noise). This retriever strips away the noise.
->How It Works-->
		1)Base Retrieval: A standard base retriever fetches a set of initial documents (e.g., top $K$ documents) based on the user's query.
		2)Compressor Execution: Each retrieved document is passed through a compressor (typically an LLM or an extraction chain) alongside the user's query.
		3)Content Filtering: The compressor evaluates the text and drops or trims out any sections, sentences, or paragraphs that do not directly address the query.
		4)Clean Output: Only the highly focused, relevant sentences or snippets are returned to the final pipeline or user.
->Why Documents Have Mixed Info-->
		This often happens because of Text Splitters during data ingestion, where a large paragraph or section gets split across boundaries, mixing distinct topics into a single document chunk.
->When to Use:
	When handling long text chunks that contain mixed or multi-topic information.
	When you want to reduce the context length sent to the final LLM and boost answer accuracy by removing irrelevant clutter.
